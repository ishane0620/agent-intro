# Agentic engineering roadmap

Twenty-five features to add to `file_agent.py`, simplest first. Each prompt is written to be pasted into Cursor as-is.

**Assumed starting point:** a single `file_agent.py` containing `TOOLS` (schema list), `safe_path`, `list_files`, `read_file`, `TOOL_FUNCS` (dispatcher dict), and `run_agent` (the loop).

**Target layout by the end:**

```
agent/
  config.py  prompts.py  loop.py  events.py  usage.py
  approval.py  sandbox.py  session.py  truncate.py
  compaction.py  skills.py  hooks.py  todo.py
  subagent.py  mcp.py  telemetry.py
  tools/   base.py  registry.py  files.py  edit.py
  providers/  base.py  anthropic.py  openai.py
cli.py  server.py  evals/
```

## Phase 1 — Foundations

| # | Feature | What it teaches | Pi reference | Detailed prompt for Cursor |
|---|---|---|---|---|
| 1 | System prompt | How much behavior comes from prose, not code | `harness/system-prompt.ts` | Create `prompts.py` with `SYSTEM_PROMPT: str` and a function `build_system_prompt(root: Path, extra: str \| None = None) -> str` that interpolates the project root path and the current date into the template. The prompt should tell the model it is a read-only code exploration assistant, that it must call `list_files` before guessing at paths, that it should prefer many small tool calls over one broad one, and that it should answer concisely with file:line references. In `file_agent.py`, import `build_system_prompt` and pass `system=build_system_prompt(ROOT)` to `client.messages.create`. Do not put the system prompt in the `messages` list — it is a separate top-level parameter. Add a `--system-extra` CLI flag that appends user text to the base prompt. |
| 2 | `grep_files` tool | Why search exists: read-everything doesn't scale | `harness/tools/` | In `file_agent.py`, add a third tool. Implement `grep_files(pattern: str, path: str = ".", max_results: int = 50) -> str` that walks `safe_path(path)` recursively, skips binary files and any directory named `.git`, `node_modules`, `__pycache__`, `venv`, or `dist`, compiles `pattern` as a Python regex, and returns matching lines formatted as `relative/path.py:42: <line text>`, truncated to `max_results` with a trailing `"... N more matches"` note. Add its schema to `TOOLS` with a description that explicitly tells the model to prefer `grep_files` over reading many files when looking for a definition or usage. Register it in `TOOL_FUNCS`. Handle `re.error` by returning the error string rather than raising. |
| 3 | Multi-turn REPL | The message list is the agent's only state | `agent.ts` | Refactor `file_agent.py` into a class. Create `agent/loop.py` with `class Agent` holding `self.messages: list`, `self.client`, `self.tools`, `self.tool_funcs`, and `self.system`. Move the existing loop body into a method `prompt(self, user_text: str) -> str` that appends the user message, runs the tool loop until `stop_reason != "tool_use"`, and returns the final text — while leaving `self.messages` populated for the next call. Add `reset(self)` that clears the list. Create `cli.py` with a `while True` input loop that constructs one `Agent` and calls `.prompt()` per line, plus slash commands `/reset`, `/messages` (pretty-print the raw message list), and `/exit`. The key point: one `Agent` instance, many `prompt()` calls, message list persists between them. |
| 4 | Streaming output | Event-driven design beats return values | `packages/ai/src/api/` | Create `agent/events.py` defining dataclasses `TextDelta(text)`, `ToolCallStarted(id, name, input)`, `ToolCallFinished(id, output, error)`, `TurnFinished(stop_reason)`. Change `Agent.prompt` in `agent/loop.py` into a generator `prompt(self, user_text) -> Iterator[Event]`, switching `client.messages.create` to `client.messages.stream(...)` and yielding a `TextDelta` per `text` event from the stream. Accumulate the final message via `stream.get_final_message()` and append that to `self.messages` — never reconstruct it from deltas. Add `prompt_sync(self, user_text) -> str` that drains the generator and joins text, so existing callers keep working. Update `cli.py` to consume events and print text deltas with `end="", flush=True`, and tool calls as dim one-liners. |
| 5 | Token and cost accounting | You can't manage context until you measure it | `agent.ts` usage tracking | Create `agent/usage.py` with `@dataclass Usage` holding `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`, and `__add__` for accumulation. Add `PRICING: dict[str, tuple[float, float]]` mapping model name to (input $/Mtok, output $/Mtok) and `Usage.cost(model) -> float`. In `agent/loop.py`, add `self.usage = Usage()` in `__init__` and accumulate `response.usage` after every API call. Emit a new `UsageUpdated(usage)` event from `agent/events.py` at the end of each turn. Add a `/usage` slash command in `cli.py` printing cumulative tokens and dollars, and print a one-line usage footer after each turn. |

## Phase 2 — Control and safety

| # | Feature | What it teaches | Pi reference | Detailed prompt for Cursor |
|---|---|---|---|---|
| 6 | `write_file` and `edit_file` | Mutation changes the entire risk model | `harness/tools/edit.ts` | Restructure tools into a package. Create `agent/tools/base.py` with `@dataclass Tool` holding `name`, `description`, `input_schema`, `fn`, and `mutating: bool = False`, plus a method `to_schema() -> dict`. Create `agent/tools/registry.py` with `class ToolRegistry` exposing `register(tool)`, `schemas() -> list[dict]`, and `call(name, **kwargs) -> str`. Move the existing three tools into `agent/tools/files.py` as `Tool` instances. Create `agent/tools/edit.py` with `write_file(path, content)` and `edit_file(path, old_str, new_str)`, both `mutating=True`. `edit_file` must require `old_str` to appear exactly once in the file and return a clear error naming the count when it appears zero or multiple times — this uniqueness constraint is the whole design. Both must return a unified diff of what changed. Update `agent/loop.py` to take a `ToolRegistry` instead of the `TOOLS`/`TOOL_FUNCS` pair. |
| 7 | Approval gating | Human-in-the-loop: the pause before acting | `harness/hooks.ts` | Create `agent/approval.py` with `class ApprovalPolicy` exposing `check(tool: Tool, args: dict) -> Literal["allow", "deny", "ask"]`, and three implementations: `AlwaysAllow`, `ReadOnly` (deny anything with `mutating=True`), and `AskOnMutate`. Add `SessionApprovals` holding a set of `(tool_name, path)` pairs the user has already approved so the same file isn't re-prompted. In `agent/loop.py`, call the policy immediately before `registry.call(...)`; on `"ask"`, yield a new `ApprovalRequested(tool_name, args, diff_preview)` event and block on a callback passed into `Agent.__init__` as `on_approval: Callable[[ApprovalRequested], bool]`. On denial, append the string `"Denied by user."` as the `tool_result` content and continue the loop — do not raise, because the model needs to see the denial and adapt. Wire a y/n/a terminal prompt in `cli.py`. |
| 8 | Sandbox execution | Defense in depth; the model is untrusted input | `docs/security.md` | Create `agent/sandbox.py` with an abstract `Sandbox` class exposing `read(path)`, `write(path, content)`, and `exec(cmd) -> tuple[int, str, str]`. Implement `LocalSandbox` wrapping the existing `safe_path` jail, and `DockerSandbox` that runs commands via `docker exec` in a named container with the project bind-mounted read-write at `/workspace` and `--network=none` by default. Add a `run_bash` tool in `agent/tools/shell.py` that goes through `sandbox.exec`, with a hard timeout, output truncation, and a deny-list for `rm -rf /`, `curl | sh`, and fork bombs. Refactor all existing tools in `agent/tools/files.py` and `edit.py` to take a `Sandbox` rather than touching `pathlib` directly. Add `--sandbox=local\|docker` to `cli.py`. |
| 9 | Parallel tool execution | Which calls are safe to run concurrently | `harness/execution/tools.ts` | In `agent/loop.py`, replace the sequential `for block in reply.content` tool loop with a scheduler. Add `agent/tools/scheduler.py` with `execute_all(registry, blocks, max_workers=4) -> list[dict]` that partitions the blocks: any block whose tool has `mutating=True` runs sequentially in the order the model requested; all non-mutating blocks run concurrently in a `ThreadPoolExecutor`. Results must be reassembled in the model's original block order before being appended, because `tool_use_id` pairing is positional in the user's mental model and order affects reproducibility. Add `Tool.parallel_safe: bool = True` and let `run_bash` set it `False`. Emit `ToolCallStarted`/`ToolCallFinished` events from worker threads through a thread-safe queue so `cli.py` rendering doesn't interleave badly. |
| 10 | Abort and cancellation | Killing a run without corrupting state | `agent-loop.ts` abort signals | Add cooperative cancellation. In `agent/loop.py`, accept `cancel_event: threading.Event` in `Agent.__init__` and check it at three points: before each API call, after each API call, and before each tool dispatch. On cancellation mid-turn, you must still append a synthetic `tool_result` for every `tool_use` block already in the assistant message — with content `"Cancelled by user."` — because the API rejects any assistant `tool_use` block without a matching result on the next request. This invariant is the entire lesson. Add `AbortedTurn` to `agent/events.py`. In `cli.py`, install a `SIGINT` handler that sets the event on first Ctrl-C and hard-exits on second. Add a test asserting `self.messages` is still a valid request payload after an abort. |

## Phase 3 — Context management

| # | Feature | What it teaches | Pi reference | Detailed prompt for Cursor |
|---|---|---|---|---|
| 11 | Session persistence | Append-only logs over mutable state | `harness/session/jsonl/` | Create `agent/session.py` with `class Session` writing JSONL to `~/.myagent/sessions/<uuid>.jsonl`. Define record types `{"type": "meta", ...}` (written once at the top: session id, cwd, model, schema version), `{"type": "message", "role": ..., "content": ...}`, and `{"type": "usage", ...}`. Expose `append(record)`, `load(path) -> list[dict]`, and `list_sessions() -> list[SessionMeta]`. Content blocks from the SDK must be serialized with a `to_dict()` helper, not `json.dumps` on the SDK object. In `agent/loop.py`, call `session.append` after every message is added to `self.messages` — append on write, never rewrite the file. Add `--resume <id>` and `--continue` (most recent) flags to `cli.py` that rebuild `self.messages` from the log. Include a `schema_version` field and a `migrate(records)` stub. |
| 12 | Output truncation | One huge tool result kills the run | `utils/truncate.ts` | Create `agent/truncate.py` with `truncate_output(text: str, limit: int = 20_000, strategy: str = "middle") -> str`. Implement three strategies: `head` (keep first N), `middle` (keep first 60% and last 40%, with `"\n... [N chars truncated] ...\n"` in between), and `tail`. Add `estimate_tokens(text) -> int` using a chars/4 heuristic. Apply truncation centrally inside `ToolRegistry.call` in `agent/tools/registry.py` rather than in each tool, so no tool can bypass it, and remove the ad-hoc `[:20_000]` slice from `read_file`. Add per-tool overrides via `Tool.output_limit: int \| None`. When truncation occurs, the returned string must tell the model it was truncated and suggest a narrower call — otherwise the model silently reasons over partial data. |
| 13 | Compaction | The hardest problem: what to forget | `harness/compaction/` | Create `agent/compaction.py`. Implement `should_compact(messages, model, threshold=0.75) -> bool` comparing estimated tokens to the model's context limit. Implement `compact(client, messages, keep_recent=6) -> list[dict]` that: (a) always preserves the first user message verbatim, (b) takes everything except the last `keep_recent` messages, (c) sends them to the model with a summarization prompt asking for files examined, findings, decisions made, and work still outstanding — explicitly instructing it to preserve exact file paths and identifiers, (d) returns a new list of `[first_user_msg, {"role": "user", "content": "<summary>"}, *recent]`. The boundary must never split an assistant `tool_use` from its matching `tool_result`; write `find_safe_split_point(messages, target_index) -> int` for this. Call `should_compact` at the top of the loop in `agent/loop.py` and emit a `CompactionRan(before_tokens, after_tokens)` event. Log the pre-compaction messages to the session file first so nothing is lost. |
| 14 | Skills | Progressive disclosure via pointers | `harness/skills.ts` | Create `agent/skills.py`. A skill is a directory under `.agent/skills/<name>/SKILL.md` with YAML frontmatter containing `name` and `description`. Implement `discover_skills(root) -> list[Skill]` scanning both the project and `~/.myagent/skills`, parsing only the frontmatter. Implement `render_skills_block(skills) -> str` producing a compact XML block of `<skill><name>..</name><description>..</description><path>..</path></skill>` entries. Inject that block into the system prompt in `prompts.py`. Crucially: do not load skill bodies into context — the prompt tells the model to `read_file` the path when a skill looks relevant. Add a `sample skill` under `.agent/skills/code-review/SKILL.md` to test with. Verify that the injected block stays under ~500 tokens for ten skills; if not, your descriptions are too long. |
| 15 | Prompt caching | Where cache breakpoints go, and why | `packages/ai` cache control | Add caching support. In `agent/loop.py`, attach `{"cache_control": {"type": "ephemeral"}}` to the final block of the system prompt and to the last content block of the second-to-last user message, giving you a stable prefix plus a rolling breakpoint. Create `agent/caching.py` with `apply_cache_breakpoints(system, messages) -> tuple` encapsulating this, plus `cache_hit_rate(usage) -> float`. The rule to encode and document in a docstring: caching only pays off when the prefix is byte-identical between calls, so anything volatile — timestamps, token counts, a rotating tip line — must live at the *end* of the context, never in the system prompt. Audit `build_system_prompt` and move the injected date after the cache breakpoint. Extend `/usage` in `cli.py` to show cache hit rate. |

## Phase 4 — Architecture

| # | Feature | What it teaches | Pi reference | Detailed prompt for Cursor |
|---|---|---|---|---|
| 16 | Provider abstraction | Normalizing wire formats; where it leaks | `packages/ai/src/types.ts` | Create `agent/providers/base.py` defining a provider-neutral message format: `@dataclass Message(role, content: list[ContentBlock])` where `ContentBlock` is a union of `TextBlock`, `ToolUseBlock(id, name, input)`, `ToolResultBlock(tool_use_id, content, is_error)`. Define `class Provider` with `stream(messages, tools, system, model) -> Iterator[Event]` and `to_wire(messages) -> Any` / `from_wire(response) -> Message`. Implement `agent/providers/anthropic.py` and `agent/providers/openai.py`. The instructive differences to handle explicitly: OpenAI puts tool results in `role="tool"` messages rather than user-role content blocks, uses `function` nesting in tool schemas, and streams tool arguments as partial JSON strings that must be accumulated before parsing. Refactor `agent/loop.py` to depend only on `Provider`, never on `anthropic` directly. Add `--provider` and `--model` flags. |
| 17 | Hook / middleware system | Extending the loop without forking it | `harness/hooks.ts` | Create `agent/hooks.py` with `class HookRegistry` supporting named hook points: `before_turn`, `before_api_call`, `after_api_call`, `before_tool_call`, `after_tool_call`, `before_compaction`, `after_turn`. Each hook receives a mutable context object and may return `None` (continue), a modified context, or a `Halt(reason)` sentinel. Implement `before_tool_call` so a hook can rewrite arguments or short-circuit with a canned result — this is what makes approval, sandboxing, and telemetry pluggable rather than hard-coded. Then refactor: move the approval check from step 7 and the truncation call from step 12 into hooks, and delete their inline calls from `agent/loop.py`. The loop should end up shorter than it was. Add `.agent/hooks.py` project-local auto-discovery. |
| 18 | Todo / planning tool | Externalized reasoning the model can revise | — | Create `agent/todo.py` with `class TodoList` holding items of `{id, content, status: "pending"\|"in_progress"\|"completed"}` in memory per session. Add a `manage_todos` tool in `agent/tools/todo.py` accepting a full replacement list, returning the rendered list back to the model. Write the tool description to require that exactly one item is `in_progress` at a time and that the list is updated before starting and immediately after finishing each item. Inject the current list into the context as a fresh user-role reminder block at the start of each turn rather than relying on the model to recall it. Add to the system prompt in `prompts.py`: use the todo list for any task needing three or more steps, skip it for single-step work. Emit `TodoUpdated` events and render the list in `cli.py`. |
| 19 | Subagents | Delegation and context isolation | — | Create `agent/subagent.py` with `spawn_subagent(parent: Agent, task: str, tool_subset: list[str], max_turns: int = 20) -> str`. The subagent gets a fresh `Agent` with its own empty message list, a restricted registry, and a different system prompt telling it to return a dense written report rather than conversational text. Only the final report string crosses back to the parent as the tool result — this isolation is the entire point, since the parent never sees the subagent's intermediate tool calls and its context stays clean. Add a `dispatch_task` tool exposing this to the model, with a description that tells it to delegate open-ended search ("find everywhere X is configured") but never delegate work where it needs to see the details itself. Enforce `max_turns` and a token budget; forward subagent events to the parent's stream tagged with a `depth` field. Block recursive spawning beyond depth 2. |
| 20 | MCP client | Tools you didn't write, discovered at runtime | `packages/protocol` | Create `agent/mcp.py` implementing a Model Context Protocol client over stdio. Implement `class MCPServer` with `connect()` spawning the configured subprocess, `initialize()` performing the JSON-RPC handshake, `list_tools() -> list[Tool]`, and `call_tool(name, args) -> str`. Map each discovered MCP tool into your existing `Tool` dataclass from `agent/tools/base.py` with a namespaced name like `mcp__<server>__<tool>` so it collides with nothing, then register it in the normal `ToolRegistry` — the loop must need zero changes, which is the test of whether your step 6 abstraction was right. Read server configs from `.agent/mcp.json` in the standard `{"mcpServers": {"name": {"command": ..., "args": [...]}}}` shape. Handle server crashes by marking tools unavailable rather than killing the agent. |

## Phase 5 — Production

| # | Feature | What it teaches | Pi reference | Detailed prompt for Cursor |
|---|---|---|---|---|
| 21 | Eval harness | Testing something non-deterministic | `packages/evals` | Create `evals/` with `cases/*.yaml` files shaped as `{name, fixture_dir, prompt, assertions: [...]}`. Implement `evals/runner.py` with `run_case(case) -> Result` that copies the fixture to a temp dir, runs the agent headless with a turn cap, and evaluates assertions of three kinds: `contains` (substring in final output), `tool_called` (named tool appeared in the trace, optionally with arg constraints), and `judge` (a separate LLM call scoring the output against a rubric, returning pass/fail plus reasoning). Add `run_all(n_trials=3)` reporting pass rate per case rather than a boolean, because a single run tells you nothing about a stochastic system. Emit a JSON report and a terminal table. Write five starting cases covering: find a definition, count files, multi-file trace, a deliberately ambiguous request, and a request that should be refused. |
| 22 | Tracing and telemetry | Debugging a 40-step run you didn't watch | `packages/telemetry` | Create `agent/telemetry.py` exporting OpenTelemetry spans. Model one root span per `prompt()` call, child spans per API call and per tool call, with attributes for model, input/output/cache tokens, stop reason, tool name, duration, and error. Implement this purely as a hook module registered against the step 17 hook points — `agent/loop.py` must not import telemetry at all, which is the architectural test. Add a `NullExporter` default and a `--trace` flag enabling OTLP export to a local Jaeger via `docker run jaegertracing/all-in-one`. Add a `ConsoleExporter` that prints a collapsed tree of the last turn for quick debugging without infrastructure. Include a `session_id` attribute on every span so traces join to the JSONL logs from step 11. |
| 23 | Steering mid-run | Accepting input while the agent is working | `agent-loop.ts` outer loop | Restructure `Agent.prompt` into nested loops. The inner loop runs until the model stops requesting tools, as now. The outer loop re-enters the inner loop when `self.pending_messages` is non-empty. Add `queue_message(self, text)` that appends to a thread-safe `pending_messages` deque, and drain it into `self.messages` at two points: after each API call completes, and after each tool batch completes — never mid-tool, or you corrupt the `tool_use`/`tool_result` pairing. In `cli.py`, run the agent in a worker thread and keep stdin readable so typing during a run queues a steering message rather than blocking. Render queued messages distinctly. Add `AgentSteered(text)` to the event types. Test: queue a message during a long `grep_files` call and assert ordering is valid. |
| 24 | Headless / server mode | Separating the agent from its terminal | `packages/server`, `modes/` | Split the entry points. Create `agent/modes/print_mode.py` with `run_once(prompt, output_format: "text"\|"json"\|"stream-json") -> int`, reading the prompt from argv or stdin, emitting newline-delimited JSON events for the streaming format, and exiting non-zero on error — this is what makes the agent scriptable in CI. Create `server.py` with FastAPI exposing `POST /sessions`, `POST /sessions/{id}/messages` returning SSE of the event stream, `GET /sessions/{id}`, and `DELETE /sessions/{id}`, backed by the step 11 session store. Both entry points must import the same `Agent` from `agent/loop.py` with zero mode-specific branching inside it — if you need an `if server_mode:` in the loop, the abstraction is wrong. Add graceful shutdown that flushes sessions. |
| 25 | Multi-surface deployment | One core, many entry points | Hermes, not Pi | Add a third and fourth surface on top of step 24's server without touching `agent/loop.py`. Create `surfaces/discord_bot.py` mapping a Discord thread to a session id, streaming edits into a single message with a rate limit, and rendering approval requests as reaction-based confirmations. Create `surfaces/cron.py` running scheduled prompts from `.agent/schedule.yaml` and delivering output to a configured webhook. Add `agent/surface.py` defining the `Surface` protocol: `render_event(event)`, `request_approval(req) -> bool`, `get_input() -> str \| None`. Reimplement `cli.py` as `surfaces/terminal.py` conforming to it. Success criterion: adding a fifth surface should touch exactly one new file. At this point, read the Hermes gateway code and compare — it is solving this same problem across twenty platforms. |
